Worldmesh is a Rust networking library for large multiplayer worlds. It runs one world on many servers, and players see one seamless place.

You write the game as if it ran on one machine. Worldmesh decides which server simulates each entity, moves entities between servers while they keep moving, delivers what entities do to each other wherever they are, and builds each player's view from every server that holds part of it.

Worldmesh does the networking and none of the game. Each entity gets an id, a position and a kind. Health, movement, inventory and every rule are components and code your game adds.

## The problem

One server runs out of room long before a big world does. The usual workarounds are visible to players:

- **Shards**: many copies of the world, and your friends are in another one.
- **Zones**: the map is cut into pieces with loading screens between them, and a crowd in one zone overloads its server while the others sit idle.
- **Instances**: separate copies of busy places.

Worldmesh keeps one world and splits the work two ways at once:

- **By entity.** Each entity is simulated by exactly one **Server Entity Group**, wherever it stands. Groups are balanced by entity count, so a crowd in one town spreads over as many groups as it needs.
- **By area.** Each **Spatial Layer Cell** owns part of the map and keeps a copy of every entity in it, from reports the groups send every tick. From those it builds players' views, routes actions aimed at an area, and answers spatial queries. Cells simulate nothing, so moving an area from one cell to another is cheap.

## The pieces

| Piece | What it does | Runs your code? |
| --- | --- | --- |
| Server Entity Group | Simulates its entities every tick, delivers actions to them, hands entities to other groups | Yes: your systems and handlers |
| Spatial Layer Cell | Keeps a copy of every entity in its area. Builds players' views, delivers events, routes actions aimed at an area, and answers spatial queries. | No |
| Orchestrator | Decides which groups and cells are in use, who owns which area, and where new entities go | No |
| Gateway | Holds players' WebSockets, checks their messages against your types, merges their views. Run as many as you need, down to one per player. | Only your `join` function |
| NATS | The bus every process talks over: one server, or a cluster of as many as you need | No |

Every role is the same binary. Your game's `main` calls `worldmesh::run(world)`, and a command-line argument picks the role.

## What a game looks like

A game is a `World` built from plugins. A plugin registers components (an entity's state), messages (commands, actions and events) with their handlers, systems that run every tick, and kinds of entity:

```rust
#[derive(Component, Clone, Serialize, Deserialize)]
struct Health(u16);

#[derive(Message, Clone, Serialize, Deserialize)]
struct Hit {
    damage: u16,
}

struct Combat;

impl Plugin for Combat {
    fn build(&self, world: &mut World) {
        world
            // Players can see everyone's health.
            .visible::<Health>()
            // A hit arrives on the next tick, wherever its target is simulated.
            .action(|me, hit: &Hit, _from| {
                if let Some(h) = me.get_mut::<Health>() {
                    h.0 = h.0.saturating_sub(hit.damage);
                }
            })
            .kind("hero", Bundle::new().with(Health(100)));
    }
}

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let mut world = World::new(WorldConfig::default());
    world
        .plugin(Movement)
        .plugin(Combat)
        .join(|_player| Spawn::new("hero", 30.5, 32.5));
    worldmesh::run(world).await
}
```

Game code always runs as one entity, through `Me`. It changes only that entity, and reaches the rest of the world with `me.send(...)`, `me.query(...)`, `me.nearby(...)`, `me.spawn(...)` and `me.emit(...)`. [Plugins, components and messages](/Worldmesh/concepts/plugins-and-components/) explains the model; the [World reference](/Worldmesh/reference/world/) lists every call.

## What's in the repository

| Path | What it is |
| --- | --- |
| `crates/worldmesh` | The library your game depends on. It puts the crates below together. |
| `crates/worldmesh-*` | One crate per role (`sim`, `spatial`, `orchestrator`, `gateway`), plus `core`, `testing` and the derive macros |
| `packages/client` | `@worldmesh/client`: snapshots, interpolation and prediction in the browser |
| `packages/debug` | `@worldmesh/debug`: the debug panel |
| `examples/hello` | Tag, the smallest complete game |
| `examples/medieval` | An isometric world with swords, bows, fireballs and bots: a server built from three plugins, and a browser client |
| `skills/` | Agent skills for building on Worldmesh |

## Status

Worldmesh is young (0.1). It works end to end and is tested, including thousands of fighting bots across groups. Scaling is manual (from the debug panel), and there's no persistence or authentication yet. The [issues](https://github.com/OminousOne/Worldmesh/issues) list what's next.
