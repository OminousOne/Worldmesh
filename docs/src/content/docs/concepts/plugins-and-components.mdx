## Worldmesh does the networking, your game does the game

Worldmesh ships no game rules: no health, no movement speed, no inventory, no AI. It gives every entity only what the networking needs, and runs everything around it:

| Worldmesh | Your game |
| --- | --- |
| Each entity's id, position (`x`, `y`), kind, and whether a player controls it | Everything else an entity is: components you define |
| Which server simulates each entity, and moving it between servers as it moves | What happens on a tick: your systems |
| Getting a player's inputs and commands to their entity, wherever it is | What an input or command does: your handlers |
| Delivering actions between entities on the next tick, never twice | What an action does to its target: your handlers |
| Spatial queries across servers | What an entity does with the results |
| Building each player's view and sending only what changed | Which components players can see |
| Showing events to the right players | What your events look like on screen |

Even walking is yours. The position belongs to Worldmesh, because it decides who can see an entity and which cell holds it, but how an input moves it is a system you write. The repository has two games built this way: `examples/hello` (tag) and `examples/medieval` (movement, combat and bots as three plugins).

## The pieces

A game is a `World` built from plugins:

```rust
let mut world = World::new(config());
world.plugin(Movement).plugin(Combat).plugin(Bots);
worldmesh::run(world).await
```

A plugin registers any of these:

| Call | Registers |
| --- | --- |
| `component::<T>()` | A **component**: a piece of an entity's state, seen only by its server |
| `visible::<T>()` | A component others can see too |
| `kind(name, bundle)` | A **kind**: a named set of components to start an entity with |
| `input::<I>()` | The **input**: what a player is holding, timed to a sub-step. One type per world. |
| `command(handler)` | A **command**: a player's request, for their own entity |
| `action(handler)` | An **action**: what one entity does to another, to an area, or to everyone |
| `event::<E>()` | An **event**: something players see happen |
| `system(stage, f)` | A **system**: code that runs for every entity, every tick |
| `system_for::<T>(stage, f)` | A system for every entity that has a `T` |

The world also says where players appear (`join`) and what every player gets when they connect (`welcome`).

```rust
struct Combat;

impl Plugin for Combat {
    fn build(&self, world: &mut World) {
        world
            .visible::<Health>()
            .component::<Cooldowns>()
            // fn use_ability(me: &mut Me, command: &UseAbility)
            .command(use_ability)
            // fn take_hit(me: &mut Me, hit: &Hit, from: &Incoming)
            .action(take_hit)
            .event::<Effect>()
            .system_for::<Dead>(Stage::Last, respawn)
            .kind(
                "hero",
                Bundle::new().with(Health(100)).with(Cooldowns::default()),
            );
    }
}
```

## Components

A component is any serde type with a name. Derive it:

```rust
#[derive(Component, Clone, Serialize, Deserialize)]
struct Health(u16);

// Named "combat.cooldowns" instead of the default "cooldowns".
#[derive(Component, Clone, Default, Serialize, Deserialize)]
#[worldmesh(name = "combat.cooldowns")]
struct Cooldowns(Vec<(Ability, u64)>);
```

A component's name defaults to its type's name in snake case. Clients see components by name, and two plugins can't register the same one.

An entity's components move with it whenever it moves to another server, so keep everything an entity needs in them.

**Visible or hidden.** A visible component is part of what others see of the entity: the players whose screen it's on, and other entities' spatial queries. Keep everything else hidden: it never leaves the entity's group, except to move with it in a handoff. Switch these around and watch what a player receives:

**Presence means something.** Components come and go with `me.insert(Dead { until })` and `me.remove::<Dead>()`, and a client sees `dead` appear and disappear. A marker with no data, like `struct Immobile;`, is often all you need.

## Kinds

A kind names the components an entity starts with:

```rust
world.kind("bot", Bundle::new().with(Health(100)).with(Brain::default()));

// Replaces the kind's default Brain.
me.spawn(Spawn::new("bot", x, y).with(Brain::new(BotMode::Aggressive)));
```

Calling `kind` again with the same name adds to it, so each plugin can give a shared kind its own components. In the medieval example, Movement adds a `Heading` to "hero" and "bot", Combat adds `Health` and `Cooldowns`, and Bots adds a `Brain` to "bot" only. Clients get each entity's kind with it.

## Messages

Commands, actions and events are messages: serde types with a name.

```rust
#[derive(Message, Clone, Serialize, Deserialize)]
#[worldmesh(name = "use")]
struct UseAbility {
    ability: Ability,
    target: Target,
}

#[derive(Message, Clone, Serialize, Deserialize)]
struct Hit {
    ability: Ability,
}
```

A message is registered as exactly one of the three. A player can send commands but never actions, so a client can't fake what one entity does to another.

**Any number of handlers.** Register a command or action handler in as many plugins as need it. Handlers run on the receiving entity in the order they were registered, and stop early if one despawns it. A quest plugin can listen for `Hit` without the combat plugin knowing it exists.

**Events** reach clients by name, as `{ "name": "effect", "data": { ... } }`. In the browser, `client.on('effect', fn)` listens for them.

## Systems and stages

A system runs once per tick for every entity, or with `system_for::<T>`, for every entity that has a `T`. A tick has three stages, and every system in a stage runs across all entities before the next stage starts:

| Stage | Use it for |
| --- | --- |
| `First` | Deciding: AI, reacting to what arrived |
| `Update` | Doing: movement, most rules |
| `Last` | Cleaning up: respawning, spatial queries for the next tick |

Commands and actions are handled before the systems run, so a hit that landed this tick is already applied when your systems see the entity.

## Plugins meet through components

Plugins don't call into each other's state. They agree on components. In the medieval example:

- Combat inserts Movement's `Immobile` when a unit dies, and Movement doesn't move anything immobile.
- Combat records the last hit a unit survived in a `LastHit` component, and Bots reads it to fight back.
- Bots steer by setting their `Heading`, the same component a player's input sets.
- Bots fight through Combat's public `use_ability`, so a bot can't do anything a player can't.

## Only change yourself

Game code always runs as one entity, through `Me`, and changes only that entity. Everything else it reads (`me.nearby`, `me.find`) or asks for (`me.send`). That's what lets any entity run on any server: nothing reaches into another entity's memory, so it doesn't matter where that entity is. More in [Entities and actions](/Worldmesh/concepts/entities-and-actions/).
