Two numbers set a world's capacity, and both can change while it runs:

- **Groups in use**: how many Server Entity Groups share the entities. This is the capacity for simulation. Group processes start as many groups as they're asked for, up to 1,000 in use.
- **Cells in use**: how many Spatial Layer Cells share the map. This is the capacity for questions, area actions and views, up to the number of cell processes running.

You set both by hand for now: `--groups` and `--spatial` on the orchestrator at start, then live from the [debug panel](/Worldmesh/guides/debug-panel/). Automatic scaling, from the load every process already reports, is on the roadmap.

## Changing the number of groups

Raising it starts new groups on the group processes running the fewest. Once they're up, the orchestrator re-splits every entity and tells each group which ones to release:

1. Sort the entities along a [Hilbert curve](https://en.wikipedia.org/wiki/Hilbert_curve): a path through every tile that keeps neighbors close together.
2. Cut the sorted list into equal runs, one per group. Each group gets the same number of entities, in a compact patch.
3. Give each run to the group that already holds most of it, so as few entities as possible move. Adding a fourth group to three moves about a quarter of them.

Lowering it hands every entity of the groups taken out of use to the rest, and stops those groups once they've been empty for a few seconds.

## A handoff

When a group releases an entity:

1. It finishes the tick, so the entity is in that tick's report and never vanishes from view.
2. It sends the entity's full record to the new group: its kind and every component, visible or not, plus Worldmesh's bookkeeping (the last tick it was simulated, its recent positions for `position_at`, the actions it already got, and its player's inputs not yet due).
3. For a second, it keeps listening for the entity and forwards anything that arrives to the new group.

The new group simulates it from the next tick, never repeating a tick the old group already ran. The player sees nothing: no pause, no lost input, no action applied twice.

## Changing the number of cells

Cells own equal runs of chunks along a Hilbert curve, so each cell's area is compact. Changing the count re-splits the runs. Nothing is handed off: groups send their next reports to the new owners, and cells rebuild everything from the reports every tick anyway.

## When a process dies

- A **group** that sends no heartbeat for 3 seconds is dropped, and its entities with it. Its players are placed again: the gateway re-joins a player missing from their own view for 3 seconds.
- A **cell** that stops is dropped, and its area is re-split among the rest.
- A **gateway** keeps nothing but connections, so its players reconnect.

There's no persistence yet, so a dead group's bots and monsters don't come back.
