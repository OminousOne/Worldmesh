## Entities

An entity is what Worldmesh needs (an id, a position, a kind, whether a player controls it) plus the components your game gives it.

```rust
pub struct Entity {
    pub id: EntityId,
    // In tiles. Where it stands decides who can see it.
    pub x: f32,
    pub y: f32,
    pub player: bool,
    // Plus its kind and components: get::<T>(), get_mut::<T>(), has::<T>().
}
```

There are two sorts:

- **Players' entities** have the player's id, from 1 to 2³¹ - 1. The orchestrator hands ids to gateways a few at a time, so ids are unique however many gateways run. Your `join` function says where players appear and as what kind. Their entities are removed when they disconnect, or 3 seconds after their gateway stops.
- **Spawned entities**, like bots, monsters and projectiles, come from `me.spawn(Spawn::new("bot", x, y))`. The orchestrator gives them ids from 2³¹ up and picks their group. `me.despawn()` removes one.

An entity's components move with it to whichever group simulates it next, so keep everything it needs in them: health, cooldowns, AI state, inventory. Visible components are what others see of it; hidden ones never leave its group except in a handoff. [Plugins, components and messages](/Worldmesh/concepts/plugins-and-components/#components) has an example to try.

## Actions

Entities affect each other only through actions. There are two ways to send one, like UDP and TCP:

| Call | If the bus drops it |
| --- | --- |
| `me.send(to, action)` | It's lost. Use it for anything the next tick replaces anyway, like "still chasing you" or a cosmetic poke. Costs nothing extra. |
| `me.send_reliable(to, action)` | It's sent again until it lands. Use it for what must land: damage, items, "you're it". |

Both reach the same handlers, so the receiver doesn't care which was used. `to` says who gets it:

| `To` | Who gets it |
| --- | --- |
| `To::Entity(id)` | That entity, wherever it is |
| `To::Area { x, y, r }` | Every entity within `r` tiles of (x, y), except the sender |
| `To::Everyone` | Every entity in the world, except the sender. Use it sparingly. |

The target runs every handler registered for that action, in its own group, in the order they were registered.

### Always the next tick

Every action is delivered on the tick after it was sent, wherever the target is: in the same group, in a group on another machine, or moving between groups. It never lands on the same tick, even within one group, and it takes no longer as long as every process keeps up. Game rules can count on it: an arrow takes one tick to land, every time.

### Sure to land

NATS delivers each message at most once, and drops messages when a process can't keep up. A `send` that's dropped is gone. A `send_reliable` is kept by the sender's group until the receiving group confirms it:

<SureDelivery />

- **Confirmations** are batched: one message per tick to each process that sent something sure.
- **Sent again** if no confirmation comes back within 400 ms, then waiting twice as long each time, up to 1 s between copies.
- **Given up** after 5 s, when the target no longer exists or its process can't be reached. It's counted in the stats, and the debug panel shows it. (On a very lossy bus it may still have landed, with every confirmation dropped.)
- **Late copies land late.** Actions from one sender can then land out of order. Each still says when it was sent (`from.tick`), so judge it by that, as below.
- **Area and everyone actions** are confirmed hop by hop: the sender's group waits for each Spatial Layer Cell, and each cell waits for every group it passed the action to. So it reaches everyone in the circle, as the cells see it.

Some things are always sure:

| Message | Delivery |
| --- | --- |
| Players' commands | Sure: the gateway keeps each one until the player's group confirms it |
| Handoffs | Sure: the old group keeps the entity until the new group confirms it arrived |
| Players' inputs | Sure, but only the latest: a newer input replaces one still unconfirmed, and the group ignores an input older than one it already applied |

:::note
Sure means sure while the processes stay up. If a group's process crashes, the sure actions it was still waiting on die with it, along with its entities ([issue #8](https://github.com/OminousOne/Worldmesh/issues/8)).
:::

### Never twice

Each action is numbered by its sender. A group remembers what each of its entities received for 10 s, longer than anyone keeps sending, and drops numbers it has already seen. A copy sent so long ago that it might have been forgotten is confirmed but not applied. So an action is never applied twice, however it was sent, even when a handoff means it arrives by two routes.

### What you can trust

An action handler gets an `Incoming`:

```rust
pub struct Incoming {
    /// Sender id, its group, its x and y, and the tick it sent this.
    pub from: Facts,
    /// Set if this was sent to an area this entity stands in.
    pub area: Option<(f32, f32, f32)>,
    /// Sent to everyone.
    pub everyone: bool,
    /// Passed on by this entity's previous group.
    pub forwarded: bool,
    /// Ties together everything one action led to.
    pub trace: u64,
}
```

The sender's group stamps `from` from the entity it simulates. Clients never fill it in, so a hacked client can't fool a range check like this one:

```rust
// Where I stood when it was sent.
let (x, y) = me.position_at(from.from.tick);
let reach = (x - from.from.x).hypot(y - from.from.y);
if reach > SWORD_RANGE {
    return; // Out of reach: nothing happens.
}
```

`me.position_at(tick)` is where the entity stood at the end of that tick, from its last 20 ticks. Judge an action by the moment it was sent, not when it lands. Otherwise a target that runs away dodges everything that was fairly in reach.

### Two sides of every ability

The medieval example splits each ability in two:

1. **The user's side**, in the user's group (a command handler or a system): alive? cooldown ready? target within reach? Then `me.send_reliable` it.
2. **The target's side**, in the target's group (an action handler): was I in reach, and in sight, when it was sent? Then apply it.

Each side checks what only it knows exactly. Neither needs the other's state.

## Commands

A command is a player's request. The browser sends it by name, like `client.sendCommand('use', { ability: 'bow' })`. The gateway checks it against the type registered under that name and delivers it to the player's own entity on the next tick. Commands are sure to arrive, exactly once.

A browser can't send a command to anyone else's entity, or send an action at all: the gateway accepts only names registered as commands, and only for the sender's own entity.

## Events

Events show players what happened. They change nothing.

| Call | Who sees it |
| --- | --- |
| `me.emit(event)` | Players who can see this entity, and its own player |
| `me.emit_at(x, y, event)` | Players who can see (x, y) |
| `me.emit_involving(event, &[ids])` | The same as `emit`, plus these players wherever they are. An archer sees "hit" even when the target is off their screen. |

Browsers get each event as `{ name, data }`, and `client.on('tagged', fn)` listens for one.
