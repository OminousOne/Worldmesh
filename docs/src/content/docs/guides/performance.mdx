These numbers come from the medieval example: 3,000 aggressive bots fighting on a 64 × 64 map, with 4 groups, 3 cells and 10 ticks per second, release builds, every process on one 2-core machine.

| Measure | Value |
| --- | --- |
| Entities per group | 750, 750, 750 and 751 |
| Busiest group | About 13% of each tick |

Almost all of it is spatial query results. Every aggressive bot queries every 200 ms, and the results list everyone in the circle. In a crowd of thousands, that's thousands of entities per query.

The fix is in your game, because only your game knows what an entity needs to know:

- **Ask only for the components you'll read**: `Query::within(r).with::<Dead>()`. The medieval bots only need to know who's dead. Asking for that alone, instead of every visible component, cut the whole bus by about 40% (see below).
- **Ask for fewer entities**: `.nearest(n)` gets only the closest few, and `.target(id)` always includes the one you care about.
- **Query less often**, or only when something changed. A bot that was just hit already knows where the attacker is.
- **Make visible only what others need.** Visible components are in every query result that asks for them and in every player's view. Field names count too: components are MessagePack with named fields, so `{"until":1234}` spends 6 bytes on the name and 3 on the value.

## Players

What a player receives depends on how much is in their view and how much of it changes. A compact snapshot costs nothing for an entity standing still, about 9 bytes for a moving one, and sends a component only when it changes.

| Player's view | Traffic |
| --- | --- |
| A few dozen entities | 10 to 25 KB/s |
| About 1,800 entities, nearly all moving and fighting | About 330 KB/s (2.9 MB/s as JSON) |

## Settings

| Setting | Effect |
| --- | --- |
| More groups | Splits the simulation. Each group's load drops roughly in proportion. Adds a little report traffic. |
| More cells | Splits view building and spatial queries. Queries near a border go to two cells. |
| More NATS servers | Spreads connections and traffic: each message goes only to the servers with a subscriber for it. |
| `chunk_size` | Smaller chunks split areas more evenly but cost more bookkeeping. 8 tiles is a good start. |
| `TICK_HZ` | Higher is smoother and more responsive, and multiplies every per-tick cost. |
| View size | Bigger views mean bigger snapshots and more cells per view. |
| Compact snapshots | On by default. JSON is about 9 times bigger in a busy fight. |
| MessagePack on the bus | On by default. JSON is about 3 times bigger: 134 MB/s instead of 44 in the fight above. |
